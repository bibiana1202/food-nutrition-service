# 개미수열 가운데 두 자리 — Node.js

`L1 = 1`에서 시작하는 개미수열의 n번째 항에서 가운데 두 문자를 반환한다. 입력 범위는 `4 ≤ n ≤ 99`이다.
이전 항을 왼쪽부터 보면서 같은 문자가 연속된 개수와 해당 문자를 차례로 기록한다.


`solution.js`의 `makeNextSequence(sequence)`를 구현한다.

1. 첫 번째 문자를 현재 문자로 정하고 개수를 1로 시작한다.
2. 다음 문자가 현재 문자와 같으면 개수를 증가시킨다.
3. 문자가 달라지면 개수와 현재 문자를 결과에 추가한다.
4. 새로운 문자를 현재 문자로 바꾸고 개수를 1로 초기화한다.
5. 반복이 끝나면 마지막 묶음을 결과에 추가한다.

그다음 `solution(n)`을 구현한다.

1. 문자열 `"1"`에서 시작한다.
2. n번째 항이 될 때까지 다음 항을 만든다.
3. 완성된 문자열 길이의 가운데 인덱스를 계산한다.
4. 가운데 두 문자를 반환한다.

기본 구현을 작성한 뒤 다음 명령으로 테스트를 실행한다.

```bash
cd 01-look-and-say
npm test
```

이전 항의 문자열 전체를 읽어 다음 항을 만드는 방식으로 구현했으며, `n = 60`까지 테스트를 통과했다.

`n = 70`부터는 전체 문자열이 매우 커져 현재 방식으로 처리하기 어렵다. 70 테스트에서는 실제로 메모리 부족으로 프로세스가 종료되었다.

`npm test`(내장 테스트, n=70 포함)를 실제로 실행한 결과다.

```bash
npm test
```

다음 단계에서는 전체 문자열을 매번 생성하지 않고 필요한 가운데 두 문자를 구하는 더 효율적인 알고리즘을 고민해야 한다. 
최종 목표는 입력 범위의 최댓값인 `n = 99`까지 처리하는 것이다.

## 테스트 라이브러리 검토

과제 요구사항 중 "테스트 주도 개발(TDD): 테스트를 먼저 작성하고 알고리즘을 작성합니다(테스트 라이브러리 사용을 권장합니다)"라는 항목이 있다. 지금까지는 Node 내장 테스트 러너(`node --test`)를 써왔는데, 이게 요구사항에서 말하는 "테스트 라이브러리"에 해당하는지 애매해서, 같은 알고리즘을 Jest로도 테스트하는 `solution1.js`를 추가했다.

## 아이디어 탐색: 길이를 미리 알면 절반만 계산해도 될까

전체 문자열을 다 만들지 않고, **길이(L(n))를 미리 예측해서 가운데 위치(`L(n)/2 + 1`)만 알아내면 결과를 구할 수 있지 않을까**라는 생각에서 출발했다. 구현하기 전에 이 전제가 맞는지부터 실측으로 확인해봤다.

**1) "절반"이 실제로 얼마나 작아지는가**

```
n	L(n)		가운데위치(L(n)/2)	전체대비 비율
10	20		10		50.0%
20	302		151		50.0%
30	4462		2231		50.0%
40	63138		31569		50.0%
50	894810		447405		50.0%
60	12680852	6340426		50.0%
65	47736936	23868468	50.0%
```

가운데 위치는 항상 정확히 전체 길이의 50%였다. n=99까지 실측 증가율(1.30361)로 추정하면 `L(99) ≈ 3.9×10¹¹`, 그 절반은 `약 2×10¹¹`로, 자바스크립트 문자열 최대 길이(약 5.4×10⁸)의 365배쯤 된다. 즉 "절반"이라고 해도 여전히 다룰 수 없는 크기다.

**2) 길이(L(n))를 내용 없이 숫자만으로 예측할 수 있는가**

같은 길이의 문자열이라도 실제 배치에 따라 다음 항의 길이가 달라지는지 확인했다.

```
"11"(길이 2)   → "21"(길이 2)
"12"(길이 2)   → "1112"(길이 4)   ← 같은 길이인데 결과 길이가 다름

"1211"(길이 4) → "111221"(길이 6)
"1112"(길이 4) → "3112"(길이 4)   ← 역시 같은 길이인데 결과가 다름
```

길이라는 숫자 하나만으로는 다음 길이를 알 수 없고, 실제 숫자 배치(어떤 숫자가 몇 번 연속됐는지)가 있어야 한다는 걸 확인했다.

**3) 그럼 일정한 비율로 근사하면 안 되나**

개미수열의 길이 증가율은 n이 커질수록 약 1.303577(Conway 상수)에 가까워진다. 이 비율로 계속 곱해서 예측한 값과 실제 값을 비교했다.

```
n	실제 L(n)	비율 예측값	오차
20	302		283.4		18.6
30	4462		4015.7		446.3
40	63138		56902.8		6235.2
50	894810		806308.3	88501.7
60	12680852	11425334.9	1255517.1
65	47736936	43008355.4	4728580.6
```

오차가 계속 누적돼서 n=65에서 이미 470만 자 넘게 차이가 난다. "가운데 두 글자"는 위치가 1자만 틀려도 완전히 다른 답이 되므로, 이런 근사치로는 정확한 위치를 찾을 수 없다.

**지금까지 결론**: "길이를 미리 예측해서 절반만 생성한다"는 이 방식은 막혔다. (2)에서 확인했듯 길이는 숫자 하나(L(n-1))만으로 정해지지 않고 실제 배치가 있어야 알 수 있는데, 그 배치를 알려면 결국 문자열을 만들어야 한다 — "생성 없이 길이를 먼저 안다"는 전제 자체가 성립하지 않는 것이다. 게다가 (1)에서 보듯 설령 길이를 안다 해도 절반은 여전히 다룰 수 없는 크기라, 이중으로 막힌 셈이다.

"전체를 다 만들지 않고 가운데만 구한다"는 목표 자체는 여전히 유효하지만, 이번에 시도한 "길이(숫자 하나)만 미리 알아내는" 방법으로는 안 된다는 게 결론이다. 다음에는 접근 자체를 바꿔서, 숫자 하나가 아니라 "재사용 가능한 더 작은 단위로 문자열을 쪼갤 수 있는지"를 살펴봐야 할 것 같다.

## 아이디어 탐색: 반복되는 패턴 단위로 쪼개서 계산하기

`"111221" → "312211"`처럼 변환될 때, 반복되는 패턴 단위로 쪼개서 계산하면 전체 문자열을 만들지 않아도 되지 않을까 하는 생각에서 출발했다.

- 부분 문자열의 종류 수를 세어봤더니(길이 3/4/5), 문자열 길이는 계속 늘어나는데 종류 수는 일정 시점 이후로 안 늘어났다. 그런데 이 사실 자체는 계산에 쓸 수 있는 정보가 아니었다 — "이런 조합들이 존재한다"는 것만 알 뿐, 그걸로 뭘 계산할 수 있는지는 알려주지 않는다.
- 그래서 겹치지 않게 고정된 자리(`0~3`, `4~7`, `8~11`...)로 잘라서, 같은 조각이 항상 같은 결과로 변환되는지 실제로 확인해봤다. 50개 occurrence 중 32개(64%)가 불일치했다.
- 원인을 보니, 조각을 어디서 잘랐든 **그 앞뒤에 어떤 숫자가 오는지에 따라 변환 결과가 달라졌다.** 조각 하나만 따로 떼어놓고는 결과를 예측할 수 없다는 뜻이다.

**결론**: 반복되는 패턴 단위로 쪼개서 계산하는 방식은 실패했다. 어떤 조각이든 앞뒤 문맥에 영향을 받기 때문에, 패턴만 보고 미리 잘라서 계산하는 접근으로는 풀 수 없었다.

**최종 상태**: `solution.js`/`solution1.js`는 n=60까지는 정상 동작하고, n=70 이상에서는 문자열이 너무 커져 메모리 부족으로 실패한다(실측 결과는 위에 정리). n=99까지 처리하는 효율적인 알고리즘은 완성하지 못한 채로 제출한다.

## 소감

처음엔 그냥 문자열을 이어 붙이면서 n번 반복하면 되는 문제인 줄 알았는데, n=70에서 실제로 메모리 부족으로 프로세스가 죽는 걸 직접 보고 나서야 "지수적으로 커진다"는 게 이론이 아니라 진짜 현실적인 벽이라는 걸 체감했다.

효율적인 알고리즘을 찾으려고 "길이를 미리 알면 되지 않을까", "반복되는 패턴으로 쪼개면 되지 않을까" 순서로 시도해봤는데, 둘 다 그럴듯해 보이다가 실제로 확인해보면 막혔다. 길이는 숫자 하나로 예측이 안 됐고, 패턴은 앞뒤 문맥에 따라 결과가 달라졌다. 

다른 사람의 풀이를 찾아보지 않고 스스로 여기까지 탐색한 게, 완전한 답을 못 찾았어도 나름 의미 있었다고 생각한다. 그리고 "이 방향이 맞다"는 근거 없이 막연히 "될 것 같다"고 느꼈던 부분들이 실측해보면 대부분 틀렸다는 것도 배웠다. 감으로 판단하지 않고 직접 코드를 돌려서 확인하는 습관이 왜 중요한지 이번에 제대로 느꼈다.
